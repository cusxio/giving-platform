# Agent guide

To add a feature, copy the nearest module in `src/modules/`. The table below is the convention. The lint rules in `oxlint.config.ts` enforce the module rules that follow it (entry points, SQL placement, platform internals, repositories in client files), and each lint message names the fix. `vite build` enforces the `*.server.ts` rule. Where the table is stricter than lint, follow the table.

## Module rules

- Import another module only through `#/modules/<m>` (client) or `#/modules/<m>/server` (server). Never use a relative path into `src/modules/`.
- Modules are flat. Import siblings with `./`. A subfolder holds only leaf files that import nothing above them, such as `auth/emails/`.
- A file named `*.server.ts` never reaches the browser. `vite build` fails with `Import denied in client environment` when client code imports one.
- SQL lives only in `*.repository.server.ts`. The module that owns a table is its only writer. `history` and `analytics` read other modules' tables and write nothing.
- Client-reachable module files never import a repository, even for types. Client-reachable means every module file except `*.server.ts`, `server.ts`, and tests.
- Workflows get infrastructure from `deps` as `Pick<Deps, ...>`. Only `src/server/` imports env, the root logger, and the neon clients.
- A `defineQuery` name is `<module>.<factory name>`, such as `history.transactionItemsOf`.
- Don't export a name that only its own file uses.
- Never name a server file `*.client.*`. TanStack Start import protection denies those files on the server.

## Errors

Every failure is one of three kinds.

- A domain error is a `TaggedError` from `<m>.errors.ts`, returned as `Result.err`. It names what happened, never how the client sees it.
- `InfraError` (`src/server/infra-error.ts`) is any database, mailer or decoder failure. `op` names the failing query or label. Workflows pass it up unchanged; nobody maps it to a domain error. `required(row, op)` turns a missing `RETURNING` row into one.
- A defect is any throw, including the `Panic` that `Result.gen` makes of a throw or a rejected await inside it. It is never caught and turned into an `Err`.

The `Db` port returns `Result`: `deps.db.run(query)`, `deps.db.batch([...])` and `deps.db.transaction(work)` answer `Err(InfraError)` instead of throwing. A transaction rolls back when `work` returns `Err` and returns that `Err`; a throw from `work` rolls back and rethrows.

Write a workflow as `Result.gen` and `yield* Result.await(...)` each step. Never throw a `redirect` or `notFound` from a workflow: inside `Result.gen` it becomes a `Panic` and a 500. Return a domain error and answer it in the action's `wire` table.

## Procedures

`src/server/procedure.server.ts` is the runner. It has two front doors with one runtime: policy, parse, run, settle.

- `defineMutation` answers an envelope: `SUCCESS`, a `BUSINESS_ERROR` per `business(...)` row, `AUTH_ERROR` when the policy refuses, `VALIDATION_ERROR` for bad input, and `SERVER_ERROR` for an `InfraError`.
- `defineRead` answers the bare value. A refused policy redirects to login (or `notFound()` when forbidden), and bad input or an `InfraError` throws a generic error, so no driver message reaches the browser. Rows are `toNotFound()` or `returning(value)`.

An action's spec has `auth`, `event`, `input`, `run` and `wire`. `wire` has exactly one row per domain error `run` can return; tsc names a missing or extra row. The wire type is derived from the spec, so `<m>.types.ts` reads it with `Awaited<ReturnType<typeof fn>>`. `src/server/procedure-bindings.test.ts` fails on a `*.functions.ts` export of any other shape than the one-line binding.

- Policies (`src/server/authorize.server.ts`): `anyone`, `anonymousOnly` (a signed-in caller is redirected home), `requireUser`, `requireSu`. The workflow's context is the policy's narrowed one, so `user` is non-null under `requireUser`.
- Input: `parseWith(Compile(schema), { trim, lowercase, convert })` returns a `Parser`; `noInput` takes none. The client's input type is `Parsed<typeof parser>`, exported as `<Name>Input`. Bound string inputs with `maxLength` when they reach a sized column.

## Login codes

A code is six digits, stored in `tokens` only as its HMAC (`deps.hashToken`) and live for `CODE_LIFETIME_MINUTES` after it is issued. A user's live codes are their unexpired, unclaimed rows of the requested mode (`findLiveTokens`): a signup code never signs in, and a login code never activates a guest. The hash is unique per user, so `request-otp.server.ts` issues a code in one batch: `deleteDeadTokensOf` removes the user's claimed and expired rows, then `createToken` inserts and, on a conflict, refreshes the live row with the same hash. That row is the same code, so it keeps its id and its check count and takes the new expiry and mode.

`verify-otp.server.ts` counts the attempt against the address, the client and the email (`checkOtpVerify`), then counts one check of every live code of the mode under `code:<id>` in one batch (`checkCodes`) before comparing any of them. A guess thus spends one check of each live code, and each code faces at most five guesses in its life, however many codes are live or addresses guess. A match on a spent code is refused. The claim, `claimTokenIfUnused`, is a compare-and-set, so two requests cannot both use one code. A wrong, missing, expired, spent or other-mode code answers `INVALID_OR_EXPIRED_OTP`; only the `reason` in the log differs.

The login path deletes no other user's rows. `/api/auth/cron` (`cleanup.server.ts`, daily in `vercel.json`, guarded by `CRON_SECRET` like the eGHL cron) deletes every claimed or expired code and every `rate_limit_attempts` row whose window started `LONGEST_WINDOW_SECONDS` or longer ago. Such a row counts for nothing, since `recordAttempt` would start it over. The constant is the longest window in `rate-limit.server.ts`, so a new or longer limit moves the cutoff with it.

## Payment gateway

`payments/gateway.ts` is the port: `deps.eghl` takes and returns only the domain types of `payments/payment-outcome.ts` (`GatewayReply`, `PaymentOutcome`, `PaymentRecord`, amounts in cents). eGHL wire fields (PascalCase) stay in three files:

- `eghl.wire.ts` holds the reply schemas and status enums.
- `eghl.outcome.ts` maps a verified wire reply or answer to a domain value. It is pure, and takes only a `Verified` value.
- `eghl.gateway.server.ts` signs, sends and verifies, and logs each wire status code (`eghl.reply.verified`, `eghl.query.answered`). It alone marks a reply `Verified`, once its signature matches, and an answer once its signature matches and it names the queried PaymentID and Amount. The local oxlint rule `payments/no-verified-cast` (`lint/payments-plugin.ts`) refuses a `Verified` cast anywhere else, except in `eghl.outcome.test.ts` and `eghl.live-replies.test.ts`, which feed the mapper wire shapes.

A signed reply never fails its settlement over a field's length. `eghl.outcome.ts` cuts `TxnMessage` and `PymtMethod` to their `payments` columns in code points and drops NUL. Card fields are never cut: a token that breaks `EghlCardFieldsSchema` (in `eghl.wire.ts`, built from the documented lengths) drops the card, a mask, expiry or type that breaks it leaves only the token, which touches a card already saved, and a holder that breaks it alone saves the card with no holder (the column is nullable). The gateway logs `payment.fields_clipped` with the field names, never their values. tsc pins each of these lengths to its column (`paymentTextFitsColumns`, `cardFieldsFitColumns`), so changing a column or a length without the other fails typecheck.

A status query answer of refunded or reversed (spec 5.3) is the `refunded` outcome, carrying `refund`, the refunded total it shows (`RefundShown`). A refunded (10) answer reads `TotalRefundAmount` (spec 2.4): `total` with its cents, `none` when absent or empty, or `unreadable`. The gateway logs `eghl.query.refund_total_unreadable` at warn for an unreadable total on an answer of any status. A reversed (9) answer undoes the whole sale, so its total is `none` and is not read. A success (0) answer that shows a refunded total above zero logs `eghl.query.refund_on_success` at warn with both amounts: the platform records the whole sale, and an operator decides what the refund means. Reversal pending stays `pending`, and so do authorized and captured, which a sale cannot reach, so the gateway logs them at error. The reply schema refuses every query-only status, so no callback or return carries a refund. A busy gateway (an internal error) is `Err(EghlGatewayBusyError)` from `queryStatus`, not an outcome. `gateway.types.test.ts` fails tsc when a PascalCase key reaches anything the port takes or returns. Handlers and the cron never import `eghl.wire.ts`.

The payment request sends `PageTimeout`, signed in its hash-key slot, from `PAGE_TIMEOUT_MINUTES` in `payment-outcome.ts`. The cron's own timing sits beside it: `RECONCILE_MIN_AGE_MINUTES`, `RECONCILE_WINDOW_DAYS` and `EXPIRE_AFTER_MINUTES`. A test keeps the page limit shorter than the cron's minimum age and its not-found expiry, so the cron never queries or expires a row whose donor can still pay on the page. A longer limit moves those with it.

## Transaction status

`src/core/transaction-status.ts` owns the vocabulary: `TRANSACTION_STATUSES` (`pending`, `success`, `failed`, `held`, `cancelled`, `refunded`), the `TRANSITIONS` table, `sourcesOf` (its inverse), and the history and analytics facets (`LISTED_STATUSES`, `COUNTED_STATUS`). The schema's status enum, the `TransactionStatus` type that `#/modules/payments` re-exports, and the history and analytics filters all derive from it. Add a status there; tsc then lists every `Record<TransactionStatus, ...>` and facet that needs an entry.

`pending` moves to `success`, `failed`, `held`, `cancelled` or `refunded`. A signed success corrects `failed` and `cancelled`: to `success` when its money matches and its `TxnID` is new to the transaction, else to `held`. A refund whose shown total is not the whole sale moves `pending`, `failed` or `cancelled` to `held`. `success`, `held` and `refunded` absorb every later answer, `failed` and `cancelled` absorb every other answer, and nothing returns to `pending`.

`cancelled` is a payment page the donor left unpaid. A buyer cancel and a page timeout send the same signed failed reply, with an empty `TxnID` and a message that says cancel, and the status query then answers the gateway's own pending with an empty `TxnID`. `decide` records that claim as `cancelled` with the reply's payments row. History lists it with its own label, totals never count it, and its receipt says the donation was not completed. That copy must not say the donor chose to leave, since a timeout looks the same. The receipt never reads a payment's message to pick its view. A late success writes a new `payments` row beside the failed one's (the receipt reads the latest, by `payments.id`), runs the card step as any success does, and logs `payment.finalize.late_success` (`from`, `source`, `transaction_id`, `provider_txn_id`). From `cancelled`, a donor who left the page paid after all, so the line is a warning. From `failed` with no recorded non-empty `TxnID` (the cron's own not-found expiry, or a cancel recorded as `failed` before the `cancelled` status), the gateway never reported a charge, so the line is a warning too. With a payments row under another non-empty `TxnID`, the gateway had reported a failure it now contradicts, so the line goes through `logAlert`. It reaches a failed or cancelled row only from a callback or a return: the cron selects only `pending` rows, and the confirming query for a failed reply runs only while the row is `pending` (`findPendingAmountInCents`), so a signed success reply is the only authority for the move, the same one that moves `pending` to `success`. A success whose `TxnID` a payments row of the transaction already carries is a conflict and goes to `held`, never to `success` and never absorbed. eGHL gives a payment's failure and its success the same `TxnID`, and a reply's signature has no nonce or time, so a donor can resend their own success from the return's query string. A recorded `TxnID` therefore cannot tell a replay of a success row an operator failed by hand from a gateway that contradicts its own failure. A person decides at eGHL. An empty `TxnID` never matches. `held` is a gateway success for other money than the row's, or under a `TxnID` the transaction already recorded. An operator resolves it with eGHL. History does not list it, totals do not count it, and its receipt says the payment is being confirmed and does not poll. A held row is safe from the cron because the cron selects only `pending` rows (`pendingTransactionsToReconcile`). The cron queries with the stored amount, and eGHL answers a query for another amount than the charged one with not found, which `decide` would expire to `failed`.

A hand-failed success row that a donor replays reaches an operator as a conflict, not a second count. Two rules keep rows out of that state:

- Never move a `success` row to `failed` by hand. Refund at eGHL and leave the row as it is.
- `refunded` absorbs a success and is never a source of `success`, so a replayed success cannot undo a refund.

`refunded` is a payment the gateway took and returned before the platform recorded it: a `pending` row whose status query, from the cron or from the query that confirms a failed reply, answers refunded or reversed. `decide` records it on either path with the answer's payments row, whose `TxnID` finds the charge at eGHL, and runs no card step. Nothing is counted, so no check on the answer's amount or currency applies; `planTransition` checks only the refunded total it shows. The writer logs `payment.finalize.refunded` at warn with the answer's `amount_in_cents`, `stored_amount_in_cents`, `refunded_amount_in_cents`, the currency, `provider_txn_id` and `method`. History lists it with its own label, totals never count it, and its receipt says the donation was refunded, that the full amount goes back to the card or account the donor paid with, and does not poll. It is reached only from `pending`. A refund made at eGHL of a donation already `success` is not synced, and syncing it is a separate feature. The cron selects only `pending` rows, so such a row stays `success` and keeps counting.

`payments/record-outcome.server.ts` is the only writer of `transactions.status`. Inside one `db.transaction` it runs `lockTransaction` (`SELECT ... FOR UPDATE`), `findProviderTxnIds` (the `TxnID` of each payments row, read after the lock), the pure `planTransition(stored, outcome)`, and on a move `moveTransaction(transition)`, the payments insert and the card step. `planTransition` holds a success whose `TxnID` a payments row carries, whose currency is not `PAYMENT_CURRENCY`, or whose cents differ from the stored amount, and, from `pending`, `failed` or `cancelled`, a refund whose shown total is `unreadable` or differs from the stored amount (`refund_mismatch`; below the sale it is a partial refund, above it the total contradicts the signed amount, and either way the refunded receipt would promise the full amount back). The total is not signed, so it can only hold a refund back, never settle one: the writer moves the row to `held` with the same compare-and-set, writes no payments row, runs no card step, and logs `payment.finalize.conflict`, `.currency_mismatch`, `.amount_mismatch` or `.refund_mismatch` with `logAlert` (both amounts, `refunded_amount_in_cents` for a refund, the currency, the status it left as `from`, and `provider_txn_id` and `method` to find the charge at eGHL). The conflict is checked first, so a conflicting success for other money logs one alert, `conflict`, whose amounts show the mismatch: the operator must first learn that the transaction already recorded this charge. A success onto a `success` row is a replay before these checks, and so is a success onto a `held` row that would itself be held. `moveTransaction` takes a `Transition` (a move or a hold) that only `planTransition` constructs, and its WHERE lists `sourcesOf(to)`, so the database refuses what the table refuses. A compare-and-set that finds no row after the lock is an `InfraError`, never a silent no-op, and so is a stored status outside the tuple. Nothing else updates a transaction's status.

Every channel settles through `payments/settlement.server.ts`: the callback and both returns call `settleReply(deps, reply, source)`, and the cron calls `settlePolled(deps, row)` once per pending row. Each asks the gateway when it must, lets the pure `decide(outcome, context)` in `payment-outcome.ts` say what the answer means for the row, and then records through `recordOutcome` or waits. Change what an answer means in `decide`, never in a handler or the cron. `oxlint.config.ts` enforces the path: only `settlement.server.ts` imports `record-outcome.server`, and only `record-outcome.server.ts` imports `lockTransaction` and `moveTransaction`.

The cron's summary, `eghl.cron.complete`, carries `stale_pending`: the count of `pending` rows older than its window (`countStalePending`), which it no longer queries. The summary is a warning when the count is not zero. A failed count is logged as `eghl.cron.failed` and leaves the field out. An operator resolves those rows at eGHL.

## Logs and traces

- The runner logs each outcome once: a row's own `event`, `<event>.unauthorized`, `<event>.validation_failed` (with `issues`), `<event>.failed` for an `InfraError`, and `<event>.defect` for a throw.
- A failure log carries `error.type` (the class, or a SQLSTATE or system code when the class is generic), `op`, and `err` with the class, code and SQL text but no query parameters or database messages. Never log a raw driver error yourself: use `logInfraFailure` or `logInfraEvent`.
- A `SERVER_ERROR` envelope is an HTTP 200, so `<event>.failed` and `<event>.defect` also mark the request span `ERROR` and record the exception. Healthy spans stay `UNSET`.
- A domain event someone must act on while the response stays healthy (a held payment answers the gateway `OK`) goes through `logAlert`, which logs it at `error` and marks the request span `ERROR` with the event as `error.type`.
- An HTTP route that is not a server function wraps its handler in `logDefects(logger, event, handler)` so a defect is logged once and rethrown.

## Lint bans

- `redirect` and `notFound` from `@tanstack/react-router` are banned in `src/modules/**/*.server.ts` and `src/server/**`. Only the runner, `eghl.http.server.ts`, `session.server.ts` (logout) and `maintenance.server.ts` throw them, all outside any workflow.
- A cast to `Verified<...>` is banned everywhere except `payments/eghl.gateway.server.ts` and the two mapper tests named under Payment gateway. In `src/modules/payments/**`, outside those three files, so is a cast to `never` or `any` (`payments/no-never-or-any-cast`), since either passes as `Verified`. Cast to the type you mean instead.
- `Panic` and `panic` from `better-result` are banned everywhere except the runner (`src/server/procedure.server.ts`), tests in `src/modules/**` (`*.test.ts`, `*.test.tsx`) and tests in `src/server/**` (`*.test.ts`). Tests elsewhere, such as in `src/core/**` or `src/routes/**`, may not import them.

## Tests

- Test pure files directly, with plain rows and no fakes.
- Test workflows by calling them with `createFakeDb()` and `testDeps(overrides)`, and read their `Result` with `okValue` or `errValue`. Don't mock env.
- Test an action by calling it with `{ context: testContext(user, deps), data }`. Assert the wire answer and the log lines from `recordingLogger()`.
- `createFakeDb().on(factory, impl)` answers a query. The `impl` type comes from the real factory, so a fake cannot drift from the query. An `impl` that throws is a failed statement: `Err(InfraError)`.
- `db.calls` lists every query with its arguments. `db.roundTrips` lists the query names each database round trip carried. Assert `roundTrips` for every workflow that batches, so a lost `db.batch` fails a test. `db.transactions` lists each transaction's `commit` or `rollback`.
- Pin exact SQL with `createDriverDb` when the statement's text matters, such as an `ORDER BY`.

## Checks

CI runs `moon ci :lint :format-check :typecheck :test :bundle :knip`. `bundle` is `vite build`, the only check that catches server code reaching the client.
